# 按 SPEC 实现

用户只在三个地方出手：中高风险时看测试、回答【需要你决定】、看最后的交付报告。其余的你自己做完。中途不要单独发"我要开始了""verify.sh 建好了"这类消息等用户回复：这些内容中高风险时并进第 3 步的消息，低风险时并进交付报告。

## 0. 读 spec
- 读用户给的路径；没给就读项目根目录的 SPEC.md。找不到就停下，建议用户先用 /spec 写一份。
- 读出风险档（低 / 中 / 高）。spec 里没写风险档的按"中"处理，并在第 3 步的消息里说明。

## 1. 确认测试能跑
- 项目没有 `.claude/verify.sh` 就建一个：
  - 优先用项目里已有的测试命令（README、Makefile、package.json、CI 配置）。
  - 开头写 `set -e` 和 `cd "$(dirname "$0")/.."`；解释器靠 PATH 找不稳时用绝对路径，因为钩子运行它时的环境和你的终端不一定一样。
  - 项目已经在用类型检查就加上；要装新依赖才能加的不加，写进报告。
  - `chmod +x`。
- 运行一次，排除环境问题（解释器版本、缺依赖、路径）。一个测试都还没有导致的"没收集到测试"不算环境问题。
- 环境有问题就停下，说清楚是什么问题、建议怎么修。装依赖、换解释器要先问用户。环境没跑通之前不往下走。

## 2. 写测试
- spec 里的每条验收例子和每条默认假设都要有测试，测试名或注释写明对应 spec 的哪一条。
- 已有测试正好覆盖了某一条（常见于防回归），可以直接复用，在对照表里标"原有测试"，不要改它的断言。"这次不做"里涉及已有行为的，确认有测试覆盖，没有就补。
- 新测试放进新文件，或者在测试函数里面再导入还不存在的函数。不要在已有测试文件顶部导入还不存在的东西，否则整个文件收集失败，原有的防回归测试也跟着挂。
- 只写测试，不写实现。
- 跑一遍 `.claude/verify.sh`，检查两件事：
  - 新行为的测试应该失败（FAIL 或 ERROR 都算），而且原因是功能还没实现（接口不存在、函数没定义、结果不对），不是测试本身写错。
  - 防回归的测试应该已经通过。
- 不符合预期的，先修测试，再往下走。
- 记下测试替 spec 做了哪些解释：spec 没写死、你自己挑了取值或理解方式的地方（例如"四舍五入"具体怎么舍、边界值算不算）。中高风险时写进第 3 步的消息，低风险时写进交付报告。

## 3. 按风险档决定要不要停下
- **低**：不停，直接进第 4 步。
- **中 / 高**：停下给用户看测试。一条消息里依次写：
  1. 一句话：要做什么、风险档是什么。
  2. verify.sh 的内容（新建的才贴）和环境检查结果。
  3. 对照表：spec 第几条 → 测试名 → 现在的结果（失败 / 通过 / 原有测试）。
  4. 失败输出的关键几行。
  5. 测试替 spec 做的解释。
  6. 最后一句："看完说'可以'我就锁住测试开始实现；哪条测得不够，直接说编号。"

  用户提了修改：改完只把改动的部分再给他看一次，直到他说"可以"。

## 4. 锁测试
运行 `~/.claude/hooks/lock-tests.sh`。锁住后不能再改测试；每次你停下来，钩子都会核对测试有没有被改动，并跑 `.claude/verify.sh`，不通过就把你打回来。不要读写或删除锁文件，守卫会拦下任何提到它的命令。

## 5. 实现
- 只改 spec 范围内需要改的文件，遵守"关键决定"和"这次不做"。
- 需要用户决定时（需求不清、某条默认假设不成立、你认为测试本身有错），在回复里写【需要你决定】，给出选项和推荐。用户定了之后，在 spec 的"变更记录"里加一行。如果要改测试，告诉用户先在终端解锁，改完再锁上。
- 跑 `.claude/verify.sh`，直到全部通过。

## 6. 审查
- 用 reviewer 子 agent 审这次改动。给它三样东西：spec 文件路径、改动文件列表、最后一次 verify.sh 的输出（它只能跑单条只读命令，自己跑不了测试）。
- 它报出影响正确性的问题：在 spec 范围内的就修，修完重跑 `.claude/verify.sh`，再审一次。最多两轮。
- 你不同意的、改了会超出 spec 范围的、或者只能靠改测试解决的问题，不要修，写进交付报告。

## 7. 交付报告
先贴最后一次 `.claude/verify.sh` 的命令和完整输出，再写报告：

```
## 交付报告：<spec 名称>（风险：<低/中/高>）
- 验收：全部通过（输出见上）
- spec 对照：<每条验收例子和默认假设 → 测试名 → ✅/❌；复用的标"原有测试">
- 测试替 spec 做的解释：<低风险必填，用户没看过测试；中高风险写"已在测试评审时确认">
- 审查员：<结论>；修了：<…>；没修：<…及原因，没有就写"无">
- 改了哪些文件：<列表，包括新建的 .claude/verify.sh>
- 变更记录：<这次新增的条目；没有就写"无">
- 没做 / 没检查 / 不确定：<…；有生成文件（如 __pycache__、build 产物）没被 .gitignore 挡住的，提醒一句>
- 你接下来：
  - <按风险档只留一行：低 = 看一眼改动摘要；中 = 看改动，重点看 <文件>；高 = 逐行看 <文件:行> 的关键逻辑，再找一位同事审 MR>
  - 在终端里 cd 到项目目录，运行 ~/.claude/hooks/lock-tests.sh --unlock 解锁，然后提交
  - 用 /retro 复盘
```
