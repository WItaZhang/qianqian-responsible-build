# 写 SPEC

SPEC 是一次改动的验收约定，一份对应一次能做完、能一次审完的改动（通常是一个 PR）。写三样：要什么、怎样算对、做法上不能让 AI 猜的关键决定（接口、数据结构、要复用或不许碰的东西、性能和安全要求）。不写实现步骤，那是实现时 AI 自己列的计划。边界情况和具体取值写成测试，SPEC 里只放代表性的例子。这一步不写任何实现代码。

## 0. 先判断要不要写、写多大
标准是能不能一次做完、一次审完：
- 一句话说得清、结果一眼能看出对错（改文案、改配置、加个参数）：告诉用户"这个不用 spec，直接做"。用户坚持要写再继续。
- 修 bug：建议走"先写复现测试 → 确认失败 → 锁测试 → 修"，不用 spec。
- 正常需求（一个 PR 装得下）：写一份 spec，不拆。
- 大需求（一个 PR 装不下：要好几天、牵涉多个模块、验收例子 10 条写不完）：先拆成 3–6 片。每片能独立验证、做完就能用：打通一条从输入到输出的窄路，不要按层拆成"先把数据层做完"。切法给用户确认后，只给第一片写 spec，后面的片写进"这次不做"。

## 1. 读代码
读和需求相关的代码（新项目没有代码就跳过），用三五句话复述现在的逻辑，请用户纠正。复述可以和第一个问题放在同一条消息里。

## 2. 只问关键问题（最多 5 个）
每个候选问题过三道筛子，三个都是"是"才问：
1. 答案会改变做法吗？
2. 代码和文档里查不到吗？
3. 猜错代价大吗（要返工，或者会伤到数据、钱、权限）？

规则：
- 一次只问一个。能给选项就给选项，标出推荐项，让用户回一个字母就行。
- 先问范围（这次做到哪、不做什么），再问有业务含义的模糊点和以后很难改的决定（数据结构、对外接口）；后者定下来写进"关键决定"。
- 验收例子不要问用户要：你先起草，让用户改。
- 没过筛的问题不问，写进"默认假设"。
- 过筛的问题明显多于 5 个，说明这一份太大，回到第 0 步拆小；只多一两个，就把最不重要的写成默认假设。

## 3. 写 SPEC.md
放在项目根目录。例外：根目录的 `spec.md` 如果是 idea-kickoff 写的产品总纲（有"目标、使用场景、核心规则"这类整体内容，或者旁边有 `plan.md`），不要覆盖或归档它，这次的 spec 直接写到 `docs/specs/<YYYY-MM-DD>-<名称>.md`，并告诉用户 /build 时带上这个路径。注意在大小写不敏感的系统（macOS 默认就是）上 `SPEC.md` 和 `spec.md` 是同一个文件。根目录已经有 SPEC.md 时，先问用户上一份做完没有：做完了就移到 `docs/specs/<YYYY-MM-DD>-<名称>.md` 归档（目录名用 specs，不要用 spec：`spec/` 目录会被测试锁当成测试文件）；没做完就问是接着改它，还是先放一边。

风险档决定之后 /build 时用户要过几道关，按最高的一条定：
- 高：涉及权限或登录、并发、删改数据或数据迁移、钱、安全。
- 低：出错能直接回滚、只影响内部或开发者、不碰数据、测试好写。
- 中：其余情况。拿不准就定中。

控制在一屏以内，格式：

```markdown
# <一句话名称>（拆了片的话：第 1 片，共 N 片）

## 目标
<要解决什么问题，一两句话>

## 风险：<低 / 中 / 高>（<一句话理由>）

## 范围
- 这次不做：<明确不做的事；后面的片写在这里>
- 动之前先问我：<需要用户确认才能做的事；没有就删掉这一行>

## 关键决定
<以后很难改、猜错代价大的做法：对外接口、数据结构、要复用或不许碰的已有代码、性能或安全要求。不写实现步骤。没有就删掉这一节>

## 验收例子
代表性的例子，一般不超过 10 条（超过了说明这份太大，或者写得太细）。每条写成"给定什么 → 期望什么"，必须能写成自动测试：
1. ...

## 默认假设（不同意就划掉）
<你替用户做的判断，一条一行。实现时发现某条不成立，停下来问用户>
- ...

## 变更记录
<!-- 实现中有新发现、或需求要变：先问用户（测试锁着时用【需要你决定】），定了以后在这里加一行：日期 · 发现了什么 → 怎么定的，再改上面对应的验收例子或默认假设。
     对应的测试要等用户解锁后再改，改完重新锁上。 -->
```

## 4. 交给用户审
用几句话讲要点，请用户重点看四处：**风险档**、**关键决定**、**默认假设**和**这次不做**，这是你替他做决定的地方。用户确认之前不开始实现。确认过的默认假设和验收例子一样，之后都要写成测试。

## 审过之后告诉用户下一步
建议用户开一个新对话，说 `/build`（spec 不在根目录 SPEC.md 时带上路径，例如 `/build docs/specs/xxx.md`）。/build 会写测试、按风险档决定要不要先给用户看测试、锁住测试、实现、自动审查，最后交一份交付报告。做完后用 /retro 复盘。
