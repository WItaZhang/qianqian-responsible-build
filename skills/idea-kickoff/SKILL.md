# Idea Kickoff：从模糊想法到第一个可用版本

目标：防止"重点模糊、做出来跟想象的不一样"。核心原则是把用户脑子里的判断标准外化成文档、样例和测试，再写代码。代码是最后一步。

整个流程分 5 个阶段。**每个阶段结束都要停下来，让用户确认后再进入下一阶段。** 不要跳阶段，不要在用户没确认时开始写代码。

---

## 阶段 1：采访（不写任何代码）

目标是**高效对齐**：只对齐真正需要用户拍板的东西，不浪费用户时间。不要调用 grill-me/grilling（它们要求逐项问到底，与此冲突）。

1. 先用一两句话复述你理解的想法。
2. **先自己查，再分流。** 能从代码库、现有文件或常识查到的事实，直接去查，不问用户。然后把每个待定点分成两类：
   - **高把握**：有明确的常规做法，或者从上下文能可靠推断，而且做错了也容易改。不提问，列进"我的默认假设"清单，每条一句话，用户不反对就算通过。
   - **需要对齐**：做错了代价大或难以返工，或者取决于用户的偏好、业务判断，或者存在多个同样合理的方案。只把这一类拿来提问。
3. **按轮批量提问。** 一轮里把当前可以回答的问题一次问完（不依赖其他未定答案的问题），编号排列。依赖本轮答案的问题放到下一轮。每轮的格式：
   - 先列"我的默认假设"（可以直接否决其中任何一条）。
   - 再列编号问题，每个问题附上推荐答案和一句话理由，措辞要做到用户回答"同意"就等于采纳推荐。
   - 用户可以只回复有异议的编号，没提到的都按推荐处理。
4. **能少一轮就少一轮。** 通常一到两轮就该收敛。只要剩下的问题都已有高把握的答案，就停止提问，进入第 6 步。
5. 用户回答含糊、且影响后续方案时才追问（例如"精准"具体指什么？什么情况算失败？）。判断哪些需要对齐时，重点检查这些方面：
   - 使用者是谁，在什么场景用？
   - 输入是什么，输出是什么，做到什么程度算"完成"？
   - 下游有哪些决策依赖它的输出？（不服务于下游决策的东西不做）
   - 哪些部分是确定流程，哪些真的需要模型自主判断？
   - 什么情况算做错了？最不能接受的错误是什么？
   - 第一版明确**不做**什么？
6. 把结论整理成 `spec.md`：目标、使用场景、输入输出、核心规则、不做的事、默认假设（标注"未经用户逐条确认"）、未决问题。
7. 把会长期影响实现的关键决策同步写进 `CLAUDE.md`，保证以后的会话都遵守。
8. 请用户审阅 `spec.md`，确认后进入阶段 2。

## 阶段 2：样例（用户审阅"期望结果"）

分工原则：**AI 生成完整样例（输入和期望输出），用户审阅并提意见。** 用户不需要自己写输出，把精力花在判断"这是不是我们想要的"。

1. 根据 spec 生成 10–20 个样例，每个都包含编号、输入、期望输出和一句话说明依据的规则。必须覆盖：
   - 典型情况
   - 边界和刁钻情况（前后矛盾、信息不完整、一次性的噪音信号、重复信息）
2. **标注重点。** 把以下样例标为 ⚠️，并写明为什么值得看：
   - edge case
   - spec 没写明、靠你推断出期望输出的样例
   - 你把握不高、或者存在多种合理输出的样例
   
   排列时 ⚠️ 样例放在最前面，典型样例放在后面，用紧凑的格式（如表格）列出，方便快速浏览。
3. 请用户审阅：重点看 ⚠️ 样例，典型样例扫一眼即可。用户只需要回复有意见的编号，没提到的就算通过。
4. 处理意见：
   - 改输出：照改。
   - 意见背后有新规则或规则冲突：把规则补进 `spec.md`，再检查其他样例是否也受影响，一起修正。
   - 用户指出漏了某类情况：补上对应样例。
   修改后只把有变动的样例给用户再确认一次，不重复展示全部。
5. 用户有自己的真实数据时，欢迎加入样例，这比生成的更有价值；但不要求用户必须提供。
6. 把确认后的样例存进 `tests/fixtures/`。

## 阶段 3：技术方案与模块计划（用户一次审阅）

按 spec 里第一版的全部范围，拆成可以并行开发的模块。技术栈、模块划分、开发顺序和验收标准放进同一份方案，让用户一次审完。

1. **技术栈。** 按层列出（例如界面、后端、数据存储、AI 模型、部署），每项给出推荐和一句理由，必要时附一个备选。已有代码的项目默认沿用现有技术栈，只对新增部分提建议。
   - 用 ⚠️ 标出后期很难更换的项，写明为什么难换、换的代价是什么。常见的有：数据库和数据结构、核心编程语言、部署平台、登录方式、存到用户那里的数据格式、收费第三方服务的专有接口。
   - 其余容易更换的项给出默认推荐即可，并在设计上保证以后好换：只在和外部技术打交道的地方加一层隔离（数据库、AI 模型服务、第三方服务、界面框架），让核心逻辑不直接依赖具体技术。不要为了"以后可能换"把所有东西都包一层。
2. **模块划分。** 按职责划分，原则是解耦、边界清晰、容易理解，但不拆得太碎：
   - 每个模块能用一句大白话说清楚做什么，并且能单独测试；第一版一般 2–5 个。
   - 每个模块独占自己的文件或目录，互不重叠；公共配置、接口定义、`spec.md` 和 `plan.md` 归主会话。
   - 如果某个模块离开另一个模块就说不清楚、也测不了，说明拆过头了，应该合并。
   - 每个模块写明：职责、负责的文件或目录、对外提供的接口、依赖哪些模块的接口、对应阶段 2 的哪些样例。涉及 AI 模型的，写明模型负责什么、代码负责什么（原则：模型负责理解，代码负责保证一致性和校验）。
   - 附一张模块关系图（文字图即可）。
3. **开发顺序：按依赖关系分波。**
   - 只依赖其他模块**接口**的，可以放在同一波并行开发，测试时用接口的替身代替对方。
   - 需要另一个模块的**真实实现**才能开发或验收的，放到后一波。
   - 把各模块接起来的工作量较大时，作为最后一波里的一个模块；只有少量接线时，由主会话在合并时完成。
   - 列出每一波包含哪些模块，并说明为什么这样排。
4. **每个模块的验收标准，分两层写：**
   - 给用户看的大白话：这个模块完成后能做到什么、对应哪些样例、明确不做什么。
   - 给执行的 AI 看的技术标准：必须通过哪些测试、怎么运行、是否需要真实环境（如真实数据库、真实 API）。这一层写进 `plan.md`，不需要用户审阅。
5. **请用户一次审阅：** 技术栈（重点看 ⚠️ 项，其余回复"同意"即全部采纳）、模块划分和关系图、开发顺序、各模块的大白话验收标准。用户可能不熟悉的设计取舍，用一句大白话解释。用户只需回复有意见的地方；如果改了某个 ⚠️ 技术选择、导致模块划分变化，只把变化的部分再给用户看。
6. 确认后，把方案写进 `plan.md`；把技术栈、模块边界、文件归属和接口规则写进 `CLAUDE.md`（或项目使用的 `AGENTS.md`），保证所有开发会话都遵守。

## 阶段 4：按波并行开发，主会话验收合并

主会话负责定接口、分发任务、验收和合并；各模块由独立的 AI 在各自的 worktree 里开发。

1. **准备基线。** 主会话先写好模块之间的接口定义（例如类型和接口文件），再建好 `.claude/verify.sh`（跑全部测试的命令，开头 `set -e` 和 `cd "$(dirname "$0")/.."`，先跑通一次排除环境问题），连同 `spec.md`、`plan.md`、样例和 `CLAUDE.md` 一起提交。每一波的 worktree 都从当时最新的主分支创建，所以每个模块都带着同一份 verify.sh。
2. **分发当前这一波。** 每个模块一个 worktree（独立分支），交给一个 AI 开发。用当前环境支持的方式：Orca 里用 orchestration，Claude Code 里用 worktree 子代理；都没有时，主会话自己创建 git worktree，给每个模块写好任务书，请用户分别开会话启动。
3. **任务书写明**：模块职责、可以改和禁止改的文件、要实现和可以使用的接口、两层验收标准和对应样例。并要求：
   - 按 `/build` 的步骤做，但写完测试**不停下等用户**：这些测试来自用户在阶段 2 审过的样例，测试质量由主会话在验收时把关。顺序是：跑通 `.claude/verify.sh` → 把验收标准和分配的样例写成测试，确认新测试都失败 → 运行 `~/.claude/hooks/lock-tests.sh` 锁住测试 → 写实现，直到 verify.sh 全部通过。锁住后每次停下都会被自动验收，不通过会被打回。
   - 不为通过测试写针对特定样例的特殊逻辑。
   - 认为测试本身有错、或者缺测试时，上报主会话，不要试图改测试或解锁。
   - 需要改接口或其他模块时，上报主会话，不得自己改。
   - 只提交自己负责的文件，不合并、不推送。
   - 完成后交 `/build` 格式的交付报告：样例和验收标准 → 测试名的对照表、测试替 spec 做的解释、运行了什么和结果、提交号、哪些还没验证、哪些只用替身或模拟数据验证过。
4. **主会话亲自验收。** 在对应的 worktree 里自己重跑测试，逐条对照验收标准，不只看报告。还要核对两件事：分配给这个模块的每个样例都有对应测试，测试没有被写弱（只查状态码、断言过宽、把被测逻辑本身 mock 掉）；报告里"测试替 spec 做的解释"没有偏离用户确认过的需求，偏离了就按第 8 步找用户。涉及权限、并发、删改数据、钱的模块，再用 reviewer 子 agent 对照 spec 和计划审一遍。用替身或模拟数据跑通的，只能证明模块自身逻辑正确，不算真实集成验收，要分开记录。不通过时，把具体失败的条目退回给同一个 AI 修改；需要改测试的，由用户在终端解锁后再改。
5. **接口变更。** 收到上报后，主会话判断：不影响用户已确认的需求和方案的，自己决定，更新接口并通知受影响的模块；会影响的，按第 8 步找用户。
6. **每一波合并。** 这一波的模块全部验收通过后，先合到集成分支，解决冲突，跑全部测试和目前能跑的阶段 2 样例；通过后由主会话直接合入主分支，不需要问用户。然后从新的主分支开始下一波。推送到远端、部署上线之前，必须先问用户。
7. **最后一波合并后**，阶段 2 的全部样例都要端到端跑通。
8. **以下情况停下来找用户：** 同一个模块退回修改 2 轮后仍不通过；需要改动用户已确认的需求或方案（包括技术栈）。其余由主会话自己处理。
9. 全部完成后，用大白话告诉用户：做了什么、验收结果、还有什么没验证（例如缺真实账号或密钥）、怎么试用，然后进入阶段 5。

## 阶段 5：用具体 case 迭代

1. 请用户用真实输入试用。
2. 当用户说"不好""不准"这类模糊反馈时，帮他转化成具体 case：输入是什么、实际输出是什么、期望输出是什么。
3. 每个问题先加进测试，再修复，然后跑全部测试，确认没有改坏别的。改动较大或涉及多个模块时，按阶段 4 的方式分发、验收、合并。
4. 第一版稳定后，新功能按大小分流：
   - 普通功能（一个 PR 装得下）：用 `/spec` 写 spec，新开对话 `/build` 实现。spec 写到 `docs/specs/` 下，不要写到根目录，根目录的 `spec.md` 是整个产品的总纲，不要覆盖或归档它。
   - 一次要做好几个功能、或者要改架构、加新模块：回到阶段 2 补样例，再到阶段 3 更新技术方案与模块计划（只审变化的部分），按阶段 4 分波并行开发。

---

## 全程规则

- 讨论和实现分开：需求想清楚就写进文档。上下文变长或进入新阶段时，建议用户新开会话，依靠 `spec.md`、`plan.md` 和 `CLAUDE.md` 延续。
- 每次改动保持小而可验证。
- 用户想跳过阶段时，可以简短说明风险，但尊重用户决定。
- 和用户用他使用的语言交流。
